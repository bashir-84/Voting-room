# هم‌رأی — نسخهٔ دوم

## مرحلهٔ اول: یک بار راه‌اندازی Supabase

1. وارد پروژهٔ room-voting در Supabase شوید.
2. SQL Editor → New query را باز کنید.
3. فایل setup-v2.sql را با یک ویرایشگر متن مثل Notepad یا VS Code باز کنید.
4. همهٔ متن آن را کپی و در SQL Editor قرار دهید و Run را بزنید.
5. باید پیام Success دریافت کنید. این فایل تراکنشی است و اتاق‌ها و رأی‌های نسخهٔ قبلی را حذف نمی‌کند. اجرای مجدد همین فایل هم امکان‌پذیر است.
6. ورود مهمان (Allow anonymous sign-ins) باید روشن بماند.

فقط کلید عمومی سایت در script.js قرار دارد؛ رمز دیتابیس یا کلید service_role لازم نیست و نباید به فایل‌های عمومی اضافه شود.

## مرحلهٔ دوم: GitHub Pages

فایل‌های index.html، style.css، script.js و supabase.js را کنار هم در ریشهٔ مخزن بارگذاری کنید.
در Settings → Pages، شاخهٔ main و پوشهٔ / (root) را انتخاب و ذخیره کنید.
فایل setup-v2.sql برای اجرا در Supabase است؛ Pages آن را اجرا نمی‌کند. بارگذاری SQL و این راهنما در مخزن برای کار سایت الزامی نیست.

## کارکرد

- دو نوع دور: انتخاب اعضای اتاق یا گزینه‌های دلخواه میزبان.
- کد دلخواه ۴ تا ۱۲ رقم یا حرف انگلیسی؛ کد خودکار چهاررقمی.
- اعداد فارسی، عربی و انگلیسی یکسان‌اند و بزرگی حروف اهمیت ندارد.
- هر نفر از یک تا حداکثر انتخاب تعیین‌شده رأی می‌دهد. این سقف است، نه الزام به پرکردن همهٔ انتخاب‌ها.
- حداکثر انتخاب تا ۵۰؛ در رأی به گزینه‌ها ۲ تا ۵۰ گزینهٔ غیرتکراری، هر کدام تا ۱۰۰ نویسه.
- در رأی به افراد، نام اعضای شروع دور خودکار تبدیل به گزینه می‌شود. رأی به خود قابل تنظیم است.
- در شروع، اسامی و واجدان شرایط تثبیت می‌شوند. ورود دیرهنگام فقط از دور بعد حق شرکت می‌دهد.
- ثبت و تغییر رأی تا پایان رسمی مجاز است. رأی همهٔ اعضا دور را خودکار نمی‌بندد.
- نتیجهٔ موقت و هویت رأی‌دهندگان تا پایان از API هم ارسال نمی‌شود.
- حالت ناشناس پیش‌فرض: انتخاب فردی برای اعضا و میزبان برنامه حتی پس از پایان افشا نمی‌شود.
- حالت با نام: بعد از پایان نام و انتخاب رأی‌دهندگان نمایش داده می‌شود. این قاعده قبل از شروع به همه اعلام می‌شود.
- ناشناس بودن در برابر مدیر فنی دیتابیس تضمین نشده است.
- نتیجه شامل تعداد رأی، درصد انتخاب از رأی‌دهندگان، میزان مشارکت، رأی‌نداده‌ها و تساوی است.
- در رأی چندگزینه‌ای جمع درصدها می‌تواند بیشتر از ۱۰۰٪ باشد. مجموع رأی گزینه‌ها برابر مجموع انتخاب‌هاست، نه لزوماً تعداد رأی‌دهندگان.
- در تساوی، همهٔ گزینه‌های بالاترین رأی مشخص‌اند؛ با صفر رأی برنده‌ای اعلام نمی‌شود.
- دور جدید مستقل است و نتیجهٔ دورهای گذشته نگه داشته می‌شود. دور تمام‌شده دوباره باز نمی‌شود.
- فقط میزبان می‌تواند تنظیمات را پیش از شروع تغییر دهد یا دور را شروع، پایان و لغو کند؛ سمت سرور هم کنترل می‌شود.

## محدودیت‌ها و جزئیات واقعی

- برای دو دستگاه، اینترنت و دسترسی هر دو به آدرس سایت و دامنهٔ پروژهٔ Supabase لازم است. دسترسی از اپراتورهای ایران مستقلاً تأیید نشده است.
- هماهنگی هر ۳ ثانیه با دریافت وضعیت سرور انجام می‌شود؛ ارسال WebSocket استفاده نشده است.
- مهلت رأی‌گیری با ساعت سرور سنجیده می‌شود و تمام درخواست‌های پس از مهلت رد می‌شوند، حتی با بسته بودن مرورگر میزبان. اگر هیچ مرورگری باز نباشد، وضعیت ذخیره‌شدهٔ «پایان‌یافته» در اولین درخواست بعدی نهایی می‌شود؛ زمان مؤثر پایان همان مهلت از پیش تعیین‌شده است.
- در این مدل، هر عضویت یک رأی دارد. دستگاه/مرورگر دیگر می‌تواند عضویت تازه‌ای بسازد؛ تضمین «یک رأی برای هر انسان» وجود ندارد.
- پاک‌کردن اطلاعات مرورگر، دسترسی مهمان و میزبان را از بین می‌برد. بازیابی نقش با نام یا کد عمومی امکان‌پذیر نیست.
- کدهای استفاده‌شده رزرو می‌مانند؛ این نسخه حذف اتاق یا آزادسازی خودکار کد ندارد.
- کد سادهٔ اتاق دعوت خصوصیِ قوی محسوب نمی‌شود و ممکن است قابل حدس باشد.
- رأی‌ها و اتاق‌های نسخهٔ قبل محفوظ‌اند، اما به مدل جدید منتقل نمی‌شوند. در نسخهٔ جدید یک اتاق تازه بسازید.
- برای استفادهٔ عمومی گسترده، کنترل سوءاستفاده و ظرفیت پلن Supabase نیاز به بررسی متناسب با مصرف دارد.

## بررسی‌های انجام‌شده

کد SQL در PostgreSQL محلی (PGlite) با چند هویت مستقل بررسی شده است: عضویت، نقش میزبان، ورود دیرهنگام، منع رأی به خود، رأی تکراری، تغییر رأی، درخواست قدیمی، محرمانگی، چندگزینه‌ای، دورهای مستقل و پایان مهلت.
رابط با DOM شبیه‌سازی‌شده و همان پایگاه داده آزمایش شده است: ساخت، تنظیمات، ثبت، تغییر، پایان و دور جدید.
اجرای این ساختار روی پروژهٔ واقعی شما و آزمایش روی دو گوشی، پس از اجرای setup-v2.sql لازم است.
